# RentFlow production-readiness audit

**2026-11-20 · Scope:** React/Vite frontend, Node/Express backend, SQLite schema and bootstrap, deployment configuration, and test suite in the original working tree. The HTTP authorization verification below was added on 2026-11-23.

## Release decision

**Hold a general production release.** The release gates are recoverable storage and controlled migrations, a reproducible deployment, transactional workflow rules, and bounded background processing. Keep delivery in simulation mode. The repository shows tenant filters and meaningful security controls. This source review did not establish a Critical cross-tenant breach or an active real-email send path.

**Verification.** Node v24.22.3 ran all 15 backend test files using `node --test --test-reporter=spec server/jobs/*.test.js server/services/*.test.js`. The executable returned 0 with **175 passed, 0 failed, 0 skipped**. `npm.cmd run lint` also passed. Tests use in-memory SQLite and a restart case with a dedicated temporary database. The tested modules cover due processing, queue lifecycle and audit, recovery, scheduler overlap, sender and DNS checks, provider readiness, preflight, templates, and unsubscribe. The suite does not boot the full Express application or test the browser and proxy together. This audit did not start the app, run database CLIs, inspect live records, or run a load test. The schema map reflects source definitions. No application files, existing database records, email settings, or React UI were changed.

## SQLite schema and ownership

| Tables | Keys, relationships and indexes |
| --- | --- |
| `companies`, `users`, `revoked_tokens` | Company ID and user ID are primary keys. Users reference companies with cascade, have globally unique email and an index on company. Revocations use JWT `jti` as primary key, reference users with cascade, and index expiration. [`db.js:78`](../server/database/db.js#L78), [`db.js:123`](../server/database/db.js#L123) |
| `quotes` | Global text primary key, nullable company FK, customer and equipment text, REAL amount, display date and checked status. Indexes cover company and company/status. The demo rows start without a company. There is no separate customer master table. [`db.js:21`](../server/database/db.js#L21), [`db.js:101`](../server/database/db.js#L101) |
| `follow_ups`, `activity_logs`, `followup_due_events` | Schedule primary key is the quote ID. Activity has its own ID. Due events deduplicate by quote and schedule timestamp. All reference quotes with cascade. Schedule time and quote/activity time are indexed. [`followups.js:10`](../server/routes/followups.js#L10), [`db.js:138`](../server/database/db.js#L138) |
| `quote_contacts`, `outbound_messages`, `recipient_suppressions` | One contact per quote, messages keyed by ID and indexed by quote/creation time, and company/email suppression primary key. Contacts and messages cascade with quotes and suppressions with companies. A partial unique index enforces one active draft per quote. [`db.js:153`](../server/database/db.js#L153), [`delivery.js:9`](../server/routes/delivery.js#L9) |
| `delivery_queue`, `delivery_attempts`, `delivery_queue_audit` | Queue has one item per message via unique FK. Queue status is indexed. Attempts and audit reference the queue with cascade and index queue/time. Queue audit installs actor and cancellation columns and triggers on insert/status changes. [`db.js:196`](../server/database/db.js#L196), [`deliveryQueueAudit.js:1`](../server/services/deliveryQueueAudit.js#L1) |
| `company_sender_settings`, `sender_domain_verifications` | One row per company via company PK/FK. Sender settings store display name and reply-to. Verification stores challenge and last DNS outcome. [`senderIdentity.js:3`](../server/services/senderIdentity.js#L3), [`senderVerification.js:23`](../server/services/senderVerification.js#L23) |
| `unsubscribe_tokens`, `delivery_preflight_audit` | Tokens use unique hash identity, store company, quote, recipient and expiry/use timestamps, and index quote. Most quote descendants inherit tenant ownership through the quote. A suppression is scoped directly by company and normalized recipient. Delivery and queue triggers cancel stale drafts or active queue items after schedule deletion or change, acceptance, opt-out, suppression or email changes. The server enables FKs. Queue/audit state changes and simulation attempt writes share a transaction. There is no composite FK binding the company and quote on a token or the company and queue on preflight history. Existing service paths supply and check those relationships.

## Findings

Critical means confirmed exposure or severe data loss in the current workflow. High means a release gate or a serious capability-specific blocker. Medium means a material risk to address in the pilot. Low means localized polish or maintainability. Findings describe static source behavior unless marked measured.

### High

| ID | Finding and evidence |
| --- | --- |
| H1 | **Storage and schema changes are tied to module imports.** [`db.js:12`](../server/database/db.js#L12) hardwires `server/storage/rentflow.db`, creates it, seeds an empty quotes table before adding tenant ownership, and runs schema installers. [`followups.js:10`](../server/routes/followups.js#L10), [`delivery.js:9`](../server/routes/delivery.js#L9) and [`deliveryQueue.js:9`](../server/routes/deliveryQueue.js#L9) install further tables, triggers and a suppression backfill at router import. API and CLI processes therefore execute different initialization paths. A CLI on a fresh file can lack route-owned schema, including `follow_ups`. The check-then-add migrations in [`db.js:101`](../server/database/db.js#L101), [`deliveryQueueAudit.js:1`](../server/services/deliveryQueueAudit.js#L1) and [`senderVerification.js:23`](../server/services/senderVerification.js#L23) can race across processes or leave a partial upgrade after failure. Even CLI dry-run imports the write-capable bootstrap before reading its flags. There is no checked-in migration ledger, backup procedure, restore verification, or configurable persistent-volume path. A redeploy with an empty mount can boot with fresh demo data. |
| H2 | **Workflow checks can become stale across SQLite connections.** Quote acceptance and scheduled-state checks are before the transaction in [`quotes.js:182`](../server/routes/quotes.js#L182). [`followups.js:229`](../server/routes/followups.js#L229) checks quote status, current schedule and simulation count before the write lock. Its simulation handler records an event even if a concurrent request removed the same schedule first. [`delivery.js:383`](../server/routes/delivery.js#L383) also reads contact and draft eligibility before taking the lock, then inserts using the earlier recipient. Outcomes across API replicas can include reopening an accepted quote, consuming the same schedule twice, or a draft with stale recipient data. The single active draft index prevents duplicates but a manual draft request racing the scheduler can receive a constraint failure. Queue approval/simulation already reads and validates within its transaction in [`deliveryQueueLifecycle.js:97`](../server/services/deliveryQueueLifecycle.js#L97). |
| H3 | **Recurring backlog scans hold the SQLite writer lock.** [`dueFollowUpProcessor.js:13`](../server/jobs/dueFollowUpProcessor.js#L13) scans all overdue scheduled rows, including previously detected schedules with active drafts. [`queueDueDrafts.js:15`](../server/services/queueDueDrafts.js#L15) repeatedly scans already-queued drafts and checks readiness before detecting that a queue row exists. [`deliveryQueueRecovery.js:120`](../server/services/deliveryQueueRecovery.js#L120) walks every active queue item and [`deliveryReadiness.js:13`](../server/services/deliveryReadiness.js#L13) prepares and executes up to five queries per item. The follow-up and reconcile jobs set a 5-second busy timeout after DB import. API bootstrap and request transactions have no explicit common lock policy. There is no explicit application journal/checkpoint policy. WAL can improve reader/writer overlap on suitable storage while SQLite still serializes writers. |
| H4 | **Recovery exceeds its child-process output limit at plausible backlogs.** [`deliveryQueueRecovery.js:145`](../server/services/deliveryQueueRecovery.js#L145) retains one result per entry, [`reconcileDeliveryQueue.js:4`](../server/jobs/reconcileDeliveryQueue.js#L4) prints pretty JSON after committing, and [`startDeliveryQueueScheduler.js:8`](../server/jobs/startDeliveryQueueScheduler.js#L8) caps stdout at 1 MiB. A synthetic serialization of healthy UUID entries with seven-character numeric quote IDs measured 203,191 bytes at 1,000 rows, 1,015,191 at 5,000 and 2,030,193 at 10,000. Thus a pass can commit then be reported as failed, and repeat the same sweep on the next tick. This test measured output shape, with no database or child worker involved. |
| H5 | **The current deployment requires implicit assumptions.** [`server/index.js:24`](../server/index.js#L24) validates the JWT secret after static imports, hardcodes CORS to the Vite development origin, and binds to loopback. [`rentflowApi.js:1`](../src/services/rentflowApi.js#L1) defaults to the visitor's localhost. This can work behind a configured same-origin local proxy, but no such deployment or production config contract exists in this tree. [`server/middleware/rateLimits.js:1`](../server/middleware/rateLimits.js#L1) imports `express-rate-limit` from an ancestor install because only the root manifest declares it. A standalone server install lacks that dependency. [`server/package.json`](../server/package.json) has a failing placeholder test script and neither package pins a Node version compatible with its runtime and build tooling. |
| H6 | **Tenant authorization policy needs confirmation before onboarding additional roles.** The two-company HTTP matrix below now covers all 34 protected endpoints for missing credentials, plus tenant ownership and administrator checks. Tenant members can still edit contacts, opt out, create/read drafts, list recipient-bearing queue rows, read attempts and mutate quotes or schedules. Child lookups sometimes follow an ownership check using only the globally unique parent ID. [`delivery.js:272`](../server/routes/delivery.js#L272), [`deliveryQueue.js:242`](../server/routes/deliveryQueue.js#L242), [`auth.js:72`](../server/routes/auth.js#L72). |
| H7 | **Real delivery is a separate release gate.** [`providerReadiness.js:50`](../server/services/providerReadiness.js#L50) uses one global provider/from configuration with tenant-specific ownership. ## Crash recovery and scale

The later [database hardening plan](database-hardening-plan.md) records measured SQLite contention and the current online backup and isolated restore-validation workflow.

A crash before a transaction commits rolls back that unit of work. Due-event uniqueness, active-draft uniqueness and one queue row per message provide database-backed deduplication. Due processing and queue insertion commit separately in [`checkDueFollowUps.js:23`](../server/jobs/checkDueFollowUps.js#L23). A crash between them leaves a draft that a later due sweep can find. Recovery revalidates active queue rows and cancels invalid items with audit triggers. It is not a general worker retry system. When a shared template configuration error throws mid-batch, the whole due transaction rolls back and the next pass can repeat the same failure. There is no per-item failure isolation.

At **100 companies and 100,000 customer/quote records**, a balanced dataset averages 1,000 quotes per tenant. A concentrated tenant drives quote payload, in-browser search and DOM size. Total due schedules and active queue backlog drive worker cost across all tenants. Historical quote count drives global ID allocation. If 10,000 active entries reach reconciliation, its current readiness loop can execute up to 50,000 lookups in addition to the candidate query and transition writes. The output measurement in H4 is reproducible evidence at that size. API latency, resource usage and SQLite lock durations remain unmeasured.

Test 100 tenants with 100,000 synthetic quotes, a largest-tenant skew and realistic histories. Include mostly future schedules, an overdue burst, 10,000 active queue items, concurrent requests and scheduler overlap, and running with the actual planned disk and deployment topology. Compare query plans before adding indexes. Capture p50/p95/p99 reads and mutations, SQLite busy count and writer hold time, event-loop delay, memory, response bytes, browser DOM/render time, queue age, job duration and recovery time. Agree launch SLOs and RPO/RTO before the run. Keep a single SQLite host if it meets those targets. Evaluate a server database when the measured write concurrency or required high-availability topology exceeds that design.

### Verified findings

- **Fixed the manual draft race in H2.** The HTTP handler read eligibility and draft existence before reserving the writer lock. Pausing it before `BEGIN IMMEDIATE` let another process create the draft and queue entry. The handler then returned 500. In a second test, committing a suppression at the same boundary led the original handler to return 201 and create a draft using stale eligibility. The handler now checks quote ownership, current contact and suppression, schedule and existing draft inside its existing immediate transaction. It returns the already committed draft with 200 or rejects the suppressed recipient with 409. Template token creation, draft insertion and activity remain atomic. [delivery.js:383](../server/routes/delivery.js#L383) · [Worker race tests](../server/jobs/workerReliability.test.js#L83)
- **Confirmed pre-commit rollback and between-commit replay.** A second due process with zero timeout got `SQLITE_BUSY` while the first held its write transaction. Abrupt termination before commit left no due events, drafts, tokens, activity or queue rows. A fresh process completed the pass. Termination after the draft commit left both tenants' drafts durable with no queue entries. Two independent retry processes filled the queue once per draft, with one due event, one draft activity, one token and one queued audit per quote. [Worker crash and replay tests](../server/jobs/workerReliability.test.js#L112)
- **Confirmed approval and simulation atomicity.** Two independent approvals produced one success, one conflict and one approval audit. Killing simulation before commit preserved the approved state and left no attempt or simulation audit. Retry committed exactly one attempt and audit, and replay returned a conflict. Company B retained its pending entry. [Queue lifecycle race test](../server/jobs/workerReliability.test.js#L142)
- **Confirmed local tick skipping and cross-process recovery revalidation.** Timer ticks during an active reconciliation did not start another local child. A separate process cancelled one invalid entry while the first was paused after its read phase. The first revalidated and reported zero cancellations, leaving one system cancellation audit and the other company's queue item intact. [Reconciliation overlap test](../server/jobs/workerReliability.test.js#L169)

### Remaining risks

Job ownership, retry timing and observability remain process-local. Recurring passes can still contend at import-time schema initialization because the CLI busy timeout is set after opening the database. The crash tests used initialized fixtures and exercised the runtime transactions. They did not qualify concurrent bootstrap, real-time 30-second child timeout behavior, production storage, or multi-replica shutdown and drain. Unbounded sweeps, repeated read work, long writer holds, and durable job progress and alerting remain open in the [database hardening plan](database-hardening-plan.md). The quote and follow-up state races elsewhere in H2 and the intended cancellation and redraft semantics in M4 remain separate work. Delivery stays in draft and simulation mode.

On Node v24.22.3, `node --test --test-reporter=spec` from `server/` yielded **201 passed, 0 failed, 0 skipped, 0 cancelled**. The isolated multi-process suite yielded **6 passed, 0 failed, 0 skipped, 0 cancelled** after reproducing the two manual draft failures. All fixtures were temporary on-disk SQLite databases.
